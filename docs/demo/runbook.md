# IncidentLab: сценарий демонстрации

Демонстрация занимает 60–90 секунд. Показываем один кейс **Catalog slowdown**, расследование запроса, действие, сохранение A, возврат к той же ситуации, независимую B и сравнение. Интерфейс и реплики для жюри — на английском.

## Подготовка

Используйте Node.js 24 LTS. В корне проекта:

```sh
npm ci
npm run dev
```

Откройте [локальное приложение](http://localhost:3000). Для чистой демонстрации нажмите **Start practice**, даже если доступна **Resume saved practice**. Новая практика использует проверенный **seed 42**. Регистрация не требуется. Для проекторного показа удобно окно шириной 1440 px; перед выступлением проверьте читаемость на самом проекторе.

Источник времени и доступных значений — `getScenarios()[0]` из движка. В текущем сценарии `checkpointMs = 20000`, `durationMs = 120000`: первая остановка **00:20**, общий горизонт сравнения **02:00**. Frontend читает эти значения из определения сценария. Скорость playback меняет скорость показа модельного времени, а **Run to end** рассчитывает тот же прогон сразу до конца.

Coach работает через серверный `POST /api/coach`. Для реального AI-ответа backend настраивает `NVIDIA_API_KEY` и `NVIDIA_MODEL` на сервере. Без них тренировка и сравнение работают, а разбор честно подписан **Rule-based recap**. Не просите жюри вводить ключ. Не помещайте ключ в клиентские переменные или демонстрационные материалы.

## Реплика перед первым кликом

> “IncidentLab is a safe place to practice your first on-call decisions. I can inspect an incident, try a change, then rewind and compare another decision against the same traffic.”

До расследования не раскрывайте причину инцидента или заранее «правильное» решение.

## Основной проход: 60–90 секунд

| Время выступления | Действие в интерфейсе | Что показать или сказать |
| --- | --- | --- |
| 0–8 с | Нажмите **Start practice**. Оставьте **4× speed**. Дождитесь автоматической остановки на **00:20** — около пяти секунд показа. | “Customers are seeing slow and failed responses. I’ll start with the evidence.” Покажите **Simulated environment** и остановившиеся часы. |
| 8–23 с | В **Request explorer** нажмите **Failed**, затем **Inspect** у первого запроса. Откройте полную историю событий под таблицей. | Покажите timeout, связанные попытки и их отметки времени. “A customer request and a database attempt are different things.” Осмотр на паузе не продвигает время. Теперь можно объяснить увиденный retry: он добавляет ещё одну попытку. |
| 23–38 с | Пока часы ровно **00:20**, в группе **API replicas** выберите **4**. Покажите одну запись в журнале решений. Нажмите **Run to end**, затем **Save attempt**. | Это **Attempt A**. Покажите последствия: 120 successful, 800 failed, 40 pending. “Scaling the API was my first hypothesis. Now I can see its consequences.” |
| 38–50 с | Нажмите **Rewind & branch**. Убедитесь, что появилась **Attempt B** на **00:20**, а replicas снова **2**. В **Maximum attempts** выберите **1**, затем нажмите **Run to end**. | “A stays intact. B starts from the same checkpoint and seed, before my first decision.” У B одно новое решение на checkpoint. |
| 50–65 с | Нажмите **Compare attempts**. Покажите таблицу **Compare the consequences** и общий горизонт **120s**. | “Same traffic, same horizon: B has 589 more successful responses and 552 fewer failures. It still has 248 failures and 3 pending customers.” Покажите attempts рядом с исходами клиентов. |
| 65–90 с | Нажмите **Get comparison debrief**. Покажите источник ответа и нажмите evidence-ссылку **Attempt B · Evidence…**, если она доступна. | “The recap is grounded in computed outcomes and inspectable events.” При `source=nvidia` видна **AI debrief**, при `source=rules` — **Rule-based recap** и предупреждение. Ссылка открывает события нужной ветки. |

Если нужно показать плавное развитие последствий, вместо **Run to end** для A выберите **8× speed** и нажмите кнопку **Play simulation**. От 20 до 120 секунд модельного времени это занимает около 12,5 секунды показа. Для B используйте **Run to end**, чтобы уложиться в общий лимит. Дополнительная анимация не меняет расчётные результаты.

## Проверенные результаты движка

`npm run demo` воспроизводит этот эксперимент настоящим движком. Действия выполняются ровно на 20000 ms, общий горизонт — 120000 ms, seed — 42:

| Метрика | A: API replicas = 4 | B: maximum attempts = 1 | B − A |
| --- | ---: | ---: | ---: |
| Unique user requests | 960 | 960 | 0 |
| Successful requests | 120 | 709 | +589 |
| Failed requests | 800 | 248 | −552 |
| Pending requests | 40 | 3 | −37 |
| Database attempts | 2 588 | 987 | −1 601 |

У A на checkpoint одно действие `set-api-replicas: 4`. У B сохранена только история строго **до** checkpoint; действие A ровно на checkpoint не переносится. Новое действие B — `set-max-attempts: 1`. Остальные настройки остаются исходными из сценария: 2 replicas, максимум 3 attempts, backoff 50 ms, кроме изменённого параметра соответствующей ветки.

Это результаты ограниченной симуляции данного кейса. Уменьшение числа попыток само по себе не определяет лучший исход; показывайте successful, failed и pending вместе. Pending означает ожидание. p95 latency описывает только успешные ответы. Не превращайте эти результаты в универсальный совет по production или оценку готовности к on-call.

Если числа отличаются, проверьте seed, время действия, журнал обеих веток и общий горизонт. Начните чистую практику и повторите шаги. Не подменяйте значения в графике или таблице вручную.

## Если coach не ответил

Дождитесь ограниченного ожидания; клиент прекращает запрос примерно через 22 секунды. При ошибке доступна **Retry coach**. Основные playback, trace, branching и comparison остаются доступны.

Если сервер вернул **Rule-based recap**, покажите этот источник и предупреждение как есть. Если HTTP-запрос завершился ошибкой, завершите демо на вычисленном сравнении: “The practice and comparison run independently of the coach.” Повторный запрос — по кнопке, без циклических попыток во время выступления.

## Сохранение и повторная демонстрация

**Save attempt** сохраняет журнал и позицию времени в браузере. После reload нажмите **Resume saved practice**. Вкладки сохраняют независимые снимки; изменения во второй вкладке не должны переписывать активную попытку первой. Повреждённое сохранение показывает сообщение с возможностью начать новую практику.

Для следующего чистого прохода используйте **New practice**. Если демонстрируете уже сохранённые A/B, прямо скажите “These are saved attempts from the same deterministic run.” Пользователь по-прежнему может начать новую практику и выбрать собственные действия.

Резервное видео записывайте с работающего продукта после проверки прохода. Этот runbook не заменяет видеозапись и не подтверждает проверку на физическом проекторе.

## Проверки перед сдачей

```sh
npm run demo
npm run typecheck
npm test
npm run build
```

Для проверки production-сборки после успешного build:

```sh
npm start
```

Браузерный QA выполняется отдельно от проверки результатов движка. Финальный отчёт о выполненных проверках и обнаруженных ограничениях ведётся отдельно; наличие этого runbook само по себе не означает, что браузерный проход уже завершён.

Необязательный runner — `tests/ui/browser-flow.mjs`. Он использует установленный Chrome и внешний Playwright runtime; зависимость не добавляется в `package.json` приложения. Запустите сервер, затем выполните:

```sh
node tests/ui/browser-flow.mjs
```

Если Playwright не доступен через обычное разрешение модулей, задайте `INCIDENTLAB_PLAYWRIGHT_MODULE` как импортируемый путь к внешнему установленному модулю. На Windows для абсолютного пути используйте `file:///C:/.../playwright/index.mjs`. `INCIDENTLAB_URL` задаёт URL работающего приложения; по умолчанию используется `http://127.0.0.1:3000`. Не меняйте командный lockfile ради QA runner.

Runner проверяет полный проход, действительные исходы A/B, быстрые повторные клики, сохранение после reload, независимость вкладок, повреждённое сохранение, явное ветвление при редактировании прошлого, отказ coach, устаревший ответ и ширину 360 px. Скриншоты рабочего продукта сохраняются в `docs/demo/screenshots/`. Успешный mock-провайдер в тесте не доказывает реальный NVIDIA inference.
